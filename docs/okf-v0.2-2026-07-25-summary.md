# okf v0.2 조사 — 종합

조사일 2026-07-25 · 대상 origin/main `cce54e8` (배포 0.1.6) · 읽기 전용, 저장소·라이브 번들 무수정

이 문서는 같은 날 독립적으로 수행된 두 조사의 종합이다. 두 조사는 **서로 다른 결론에 도달했고,
그 충돌을 평균 내지 않고 그대로 드러낸 뒤 해소한다**(전역 Rule 7).

| 문서 | 질문 | 규모 |
|---|---|---|
| [okf-v0.2-2026-07-25-spec-conformance.md](okf-v0.2-2026-07-25-spec-conformance.md) | OKF **스펙** v0.2에 맞추려면 무엇을 고쳐야 하는가 | 서브에이전트 16개 |
| [okf-v0.2-2026-07-25-reliability.md](okf-v0.2-2026-07-25-reliability.md) | 이 **플러그인**의 다음 릴리스에 무엇이 들어가야 하는가 | 서브에이전트 23개 |

두 조사 모두 영역별 **적대적 검증 에이전트**를 따로 두어, 제시된 `파일:라인`·URL 근거를 직접 열어
반박을 시도하게 했다. REFUTED 판정을 받은 주장은 본문에서 제거하고 각 문서의 마지막 절에
폐기 이유와 함께 남겼다 — 그 목록이 이 조사의 신뢰성 근거다.

---

## 0. 먼저: "okf v0.2"는 스펙 버전이다

Google Cloud가 2026-07-24 OKF 스펙을 v0.2로 올렸고(커밋 `780fe9d`, PR #227), 2026-07-25에
[블로그로 발표](https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals?hl=en)했다
("OKF v0.2 adds trust signals"). 이 플러그인의 버전(0.1.6)과는 별개 축이다.

**변경 내용은 전부 선택 필드 추가이며, 하위호환이 보장된다.** PR #227이 명시한다 —
*"v0.1 bundles remain valid v0.2 bundles."*

| 신규 | 뜻 |
|---|---|
| `sources: [{resource, id, title, author, usage_count, last_modified}]` | 출처와 그 신뢰 신호 |
| `generated: {by, at}` | 누가·언제 만들었나 (`timestamp`를 대체) |
| `verified: [{by, at}]` | 독립 확인 이벤트 → 소비자가 신뢰 등급을 파생 |
| `status: draft\|stable\|deprecated` | 생애주기. 부재 시 `stable` |
| `stale_after: YYYY-MM-DD` | 절대 날짜. `today >= stale_after`면 stale |
| actor 규약 `<producer>/<version>` · `human:<id>` · `process:<id>` | `human:` 접두가 human-reviewed를 가른다 |
| type `Attested Computation` | 실행 가능한 계산의 검증. 우리 도메인 아님 |

적합성 3조건(파싱 가능 프론트매터 / 비어있지 않은 `type` / 예약 파일 구조)은 **v0.1과 동일**하고,
소비자는 선택 필드 누락·미지 type·미지 키·깨진 링크·`index.md` 부재를 이유로 번들을 거부할 수
없다(MUST NOT). **지금 우리 번들은 부적합이 아니다. 긴급 장애가 아니다.**

### 함정 하나 — 선언과 생산은 붙어 다녀야 한다

`timestamp` 폴백은 소비자 **MAY**다(SPEC §13.1 원문: *"Consumers MAY fall back to a legacy
`timestamp` when `generated` is absent."*). 따라서 `okf_version`을 `"0.2"`로 올리면서
`generated`를 생산하지 않으면, 폴백을 구현하지 않은 소비자에게 우리 concept는 **시간 신호가 아예
없는 문서**가 된다. 순수 후퇴다. **둘 다 하거나, 둘 다 하지 마라.**

## 1. 두 조사가 합의한 것

- 스펙 v0.2는 우리를 깨지 않는다. 대응은 기회이지 의무가 아니다.
- `verified`·`stale_after`·`sources`를 **자동 생성해서는 안 된다.** 배치가 자기 산출물에
  `verified`를 찍는 것은 신뢰 신호 위조이고, `stale_after`는 도메인 근거가 없으며, `sources`는
  digest가 URL을 통째로 버려서(`lib/digest.mjs:43`) 강제하면 환각만 나온다.
  Google 레퍼런스 구현도 자동 파이프라인이 만든 51개 concept 전부가 unverified이고,
  `verified`/`stale_after`가 붙은 것은 손으로 큐레이션한 데모 번들뿐이다.
- `status: deprecated`는 지금 채택할 가치가 있다 — 이 시스템에 없는 "은퇴" 수단을 스펙 정합적으로
  준다.
- `lib/lint.mjs:130`이 `timestamp`를 권장 필드로 강제하는 것은 제거해야 한다. 폐기된 필드를
  배치에게 계속 쓰라고 지시하는 셈이다.
- **게이트는 이미 포화다.** 라이브 번들 concept 22개 중 12개만 주입되고 바이트 캡이 100%
  차 있다(9,000/9,000B). 줄 캡(120)은 50줄만 써서 사실상 비활성이다. 번들을 2배·5배·10배로
  키워도 주입은 12개에서 고정된다 — 게이트는 번들 크기와 무관한 상수 창이다.
  *(이 세션 자신에게 주입된 게이트가 증거다: `patterns 2/5`, `references 1/6` … 21개 중 10개.)*
- 이미 반증된 방향(번들이 커질수록 싸진다, 체인이 진행될수록 싸진다)을 다시 밀지 않는다.

## 2. 두 조사가 갈라진 것

|  | 스펙 준수 조사 | 신뢰성 조사 |
|---|---|---|
| 다음 릴리스의 성격 | **스펙 대응** | **신뢰성** |
| 플러그인 버전 | `0.1.7` (스펙 추종에 minor를 주지 마라) | `0.2.0` (기본값이 바뀌므로 minor) |
| `generated` 스탬핑 + `okf_version` 승격 | **지금, 원자적으로** | v0.3로 미룸 |
| 근거 | 스펙이 준 것 중 우리가 정직하게 채울 수 있는 유일한 필드이고, 그 값은 코드가 전부 안다 | 전 번들 변환을 실행할 배치·락·롤백 경로를 지금 신뢰할 수 없다 |

### 해소 — 반대 근거가 실제 제안을 겨냥하지 않는다

신뢰성 조사가 스펙 작업을 미루자는 이유는 **"기존 사용자 번들 전체를 건드리는 마이그레이션"**의
위험이다. 그런데 스펙 조사가 실제로 제안한 마이그레이션은 그게 아니다 — 그 문서 §5의 결론은
**"concept 프론트매터 변환은 하지 않는다"**이고, 근거도 스펙이 아니라 데이터다:

- `generated.by`를 채울 기록이 존재하지 않는다. git 커밋 19개가 전부 고정 신원
  (`OKF Batch <okf-batch@localhost>`)이고, 배치 로그 5개에 모델 문자열 0건이다. `by`는 항목 내
  REQUIRED라 "`at`만 넣기"도 불가능하다.
- `timestamp` → `generated.at` 기계 복사는 위조다. **22개 중 4개(18%)가 8~10일 틀렸다** —
  한 파일은 자기가 존재하기 8일 전 날짜를 달고 있다. v0.1 `timestamp`는 규정이 느슨해 이래도
  위반이 아니었지만, `generated.at`은 "마지막 유의미한 변경"이라 **명백히 틀린 값**이 된다.

즉 실제 제안은 **루트 `index.md`의 `okf_version` 한 값**과 **앞으로 배치가 건드리는 파일에만
붙는 스탬프**뿐이고, 마이그레이션 코드는 0줄이다. 신뢰성 조사의 반대는 이미 기각된 설계를
겨냥하고 있다.

**그래도 순서는 신뢰성이 먼저다.** 스펙 조사의 항목 중 셋은 스펙 채택이 아니라 **결함 수정**이며,
신뢰성 릴리스로 넘어가야 한다:

- `lib/lint.mjs:130`의 `timestamp` 강제 제거 — 폐기된 필드를 계속 파는 것을 멈추는 일.
  (부수 효과가 크다: 이 경고가 `formatReport`를 통해 repair 프롬프트로 새어 들어가
  `{{LINT_REPORT}}`에 실리므로, repair가 한 번 돌면 모델이 `timestamp`를 되살린다.)
- `lib/bootstrap.mjs`에 배치 락 가드 추가 — bootstrap이 락을 확인하지 않아, 배치 청크 중간에
  새 세션이 시작되면 bootstrap의 쓰기가 트리를 dirty로 만들어 **배치의 유실 감지 백스톱을
  건너뛰게 한다**. 위치가 중요하다: 커밋(`:113`) 앞이 아니라 **SCHEMA 동기화 블록(`:91`) 앞**이다.
- 루트 `index.md`의 미지 프론트매터 키 보존 — 지금은 재생성마다 파괴한다. `regenerateIndex`가
  `runLint`보다 먼저 돌아서 경고조차 안 뜬다. 거부가 아니라 **소리 없는 삭제**다(SPEC §4.1 위반).

### 권고 순서

1. **0.2.0 — 신뢰성.** 신뢰성 조사 항목 1~9 + 위 결함 수정 3건.
2. **0.2.1 — 스펙.** `generated` 스탬핑 + `okf_version` 승격 + SCHEMA/ingest 프롬프트 갱신.
   원자적으로 한꺼번에. 이 순서는 신뢰성 조사가 자기 열린 질문 9번에서 스스로 제시한
   "선점을 우선한다면 유일하게 안전한 경로"와 같다.

**"okf-system v0.2"라는 문자열은 쓰지 마라.** 플러그인 버전과 스펙 버전이 우연히 같아 생기는
혼동이고, 스펙이 v0.3을 내는 순간 대응 관계가 깨진다. 릴리스 이름은
"okf-system 0.2.0 — 신뢰성", 스펙 표기는 번들 루트 `index.md`의 `okf_version`이 정본이다.

## 3. 조사가 새로 찾은 것 중 가장 무거운 것

스펙과 무관하게, 신뢰성 조사가 **실행으로 재현한** 결함들이다. 상세와 근거는 각 문서에 있다.

1. **프라이버시 약속이 코드에서 깨진다.** 유일한 옵트아웃인 `capture_exclude_cwd`가 제외 루트
   자신을 막지 못한다 — `lib/glob.mjs`가 `**`를 `.*`로만 치환해 선행 `/`가 리터럴로 남는다.
   실행 확인: `matchGlob('/Users/me/secret', ['/Users/me/secret/**']) === false`.
2. **설치 즉시 과거 7일치 전 프로젝트 대화가 유료 배치로 나간다.** 첫 SessionStart가 배치를
   띄우고 sweep이 `SWEEP_LOOKBACK_DAYS = 7`로 돈다. README에 이 사실이 없다.
3. **돈이 보이지 않고 천장이 없다.** Claude CLI가 `--output-format json`으로 회차별
   `total_cost_usd`를 이미 무료로 돌려주는데, `runClaude`가 그 값을 벤치 전용 환경변수 게이트
   안에서만 파일로 흘리고 호출자에게는 버린다. 로그 5개 263줄에 cost/usd/token 문자열 0건.
   더 나쁜 것은 `batch_interval_hours` 게이트가 spawn 시점에만 있고 링거 루프가 반복 호출하는
   `runBatch()` 내부에는 간격 검사가 없다 — 달러 상한이 존재하지 않는다.
   실측 기준점은 저장소 안에 이미 있다: v4 체인 실제 배치 60회 중앙값 **$0.44/회**.
4. **유입의 94%가 쓰레기다.** raw 443개 중 실사용 세션은 21~27개(5~6%). 번들에서 가장 큰
   concept 파일이 OKF 자기 버그 기록으로, 전체 concept 텍스트의 22.4%를 차지한다.
5. **되돌릴 수단이 없다.** 게이트의 references 슬롯 2개를 번들 자신이 "무관한 벤치마크 잡음"이라고
   선언한 묘비 문서가 점유하고 있는데, 파일명 사전순 때문에 실제 문서가 대신 잘린다.
   `status: deprecated`가 이 문제의 스펙 정합적 해답이다.
6. **YAML 날짜 지뢰.** 따옴표 없는 `stale_after: 2026-12-31`은 `Date` 객체로 파싱되고
   `"2026-07-25" >= <Date>`는 NaN 비교라 **어떤 날짜에도 false**다(경과일로도 false 확인).
   따옴표를 씌우면 문자열로 남아 **같은 필드가 번들마다 타입이 다르다**. 지금은 아무도 이 값을
   읽지 않아 잠복 중이고, stale/trust 로직을 **추가하는 순간** 터진다. `verified`의 bare mapping을
   1원소 리스트로 취급하라는 MUST도 같은 이유로 정규화 헬퍼가 선행해야 한다.
7. **벤치마크가 잰 적 없는 구간에 실사용자가 이미 들어와 있다.** v3 리포트가 스스로 적었다 —
   *"게이트 캡에 도달한 레벨: 없음."* $151을 쓴 두 벤치마크가 측정한 것은 concept 8개·1개짜리
   번들이고, 라이브 번들은 캡 100% 포화 상태다.

## 4. 사용자 결정이 필요한 것

에이전트가 정하면 안 되는 것만 추렸다. 각 문서에 더 자세한 목록이 있다.

1. **릴리스 커트라인.** 신뢰성 조사의 15개 항목은 한 릴리스로 과하다. 권고는 1~9다.
2. **`batch_max_usd_per_day` 기본값.** $0.44/회 기준으로 하루 몇 회를 허용할 것인가.
   `0`(무제한)을 기본으로 두면 위 3번의 구조적 위험이 그대로 남는다. 구독 사용자에게는 달러가
   아니라 플랜 한도가 실제 단위라는 점도 고려해야 한다.
3. **`schema_version`을 올릴 것인가.** 올리면 기존 사용자의 `SCHEMA.md` 로컬 편집이 템플릿으로
   덮인다(라이브 번들에서 이미 한 번 발동한 경로다 — 커밋 `0aab3b8`). 안 올리면 새 규정이 기존
   번들에 **영원히 전파되지 않는다.** 중간 선택지가 코드에 없다. 스펙 작업의 SCHEMA 갱신이
   여기 걸린다.
4. **`generated.by`에 무엇을 쓸 것인가.** `okf-system/<실제 모델>`(레퍼런스 관행과 동형) 대
   `okf-system/<플러그인 버전>`. 권고는 전자, 폴백 `okf-system/unknown`.
5. **라이브 번들 오염 4건을 직접 정리할 것인가.** 사용자 번들 편집이라 승인이 필요하다.
   정리하지 않으면 게이트 references 슬롯 낭비가 릴리스 후에도 그대로다.
6. **기본 언어를 en으로 전환할 것인가.** 런타임(프롬프트·SCHEMA·게이트)이 100% 한국어인데
   README는 8개 언어다. 전환하면 본인 번들의 게이트가 영어가 된다.
7. **선점 대 안전.** 경쟁 구현체 2종은 전부 v0.1이고 아직 아무도 v0.2 배지를 달지 않았다.
   이 선점 가치는 **측정된 적 없는 마케팅 가설**이다. 조사 권고는 신뢰성 우선이다.

## 5. 이 조사의 한계

- **제3자 v0.2 반응은 관측 0건.** 발표 다음날이라 2차 자료가 전부 v0.1 시기다.
  "아무도 아직 대응 안 했다"는 내부 우선순위 근거일 뿐 대외 주장거리가 아니며 며칠이면 낡는다.
- **외부 validator 미실행.** 우리 lint 통과는 우리 규칙 통과일 뿐 스펙 통과의 증거가 아니다.
  Google 저장소에는 별도 conformance 검사기가 없다(레퍼런스의 REQUIRED는 `type` 하나로,
  **우리 lint가 더 엄격하다**).
- **유료 벤치마크 미실행**(의도적). 게이트 주입 품질 변화의 정량 검증은 없다.
