# OKF E1 — 사전등록서: 게이트 recall@cap ($0)

**대상**: `docs/0-2_develop_plan.md`의 **I6**(측정 설계: `lib/gate.mjs` 추출 + recall@cap 사전등록 실험).
**진입 게이트**: 같은 문서의 **G3-0a ~ G3-0f**.
**비용**: $0. 유료 LLM 호출을 한 건도 내지 않는다. 이것은 선언이 아니라 아래 §7의 PATH 트랩으로 **실행 중에 증명**된다.

이 문서는 리포트(`gate-recall-2026-07-26-e1.md`)보다 **먼저 커밋**된다. G3-0f가
`git log --diff-filter=A`로 그 순서를 기계 검사한다. 같은 커밋에 담는 것은 위반이다.

## 0. 이 문서가 언제 쓰였는가 — 먼저 밝힌다

사전등록의 가치는 **기준이 결과보다 앞선다**는 데 있다. 그 순서가 어디까지 지켜졌는지를 먼저
정확히 적는다. 이 절을 흐리면 나머지가 전부 장식이 된다.

- **반증 기준 R1~R5의 임계값과 예측 P1~P5는 이 문서에서 새로 정하지 않았다.** 전부
  `docs/0-2_develop_plan.md`(I6, 라인 2321~2322)에서 **문자 그대로** 옮겨 왔다. 그 텍스트는
  커밋 `ba961c5`(PR #16, `main`에 머지됨)에 들어 있고, 이 브랜치에서 계획서는 **한 글자도
  수정되지 않았다**(`git diff origin/main -- docs/0-2_develop_plan.md`가 빈 출력).
  → 임계가 측정보다 앞선다는 것은 기계적으로 확인 가능하다.
- **그러나 이 문서를 작성한 시각은 하니스 검증 실행보다 뒤다.** 하니스(`test/gate-recall.mjs`)는
  존재하지 않았고, 만들어서 돌려보지 않고는 "돈을 안 쓴다"·"결정적이다"·"예산이 라이브와
  같다"를 확인할 방법이 없다. 그 검증 실행이 곧 recall 숫자를 낳았다.
- 따라서 **이 문서를 쓰는 시점에 이미 알고 있던 것**을 숨기지 않고 아래 §9에 그대로 적는다.
  숫자를 본 뒤에 임계를 움직이지 않았다는 것이 이 사전등록이 주장하는 전부이고, 그 이상을
  주장하지 않는다.

**이 문서가 확정한 뒤로는 어떤 임계도 완화하지 않는다.** 특히 R3이 발화하면 발화한 것으로
발행한다(§6 참조). "노이즈였다"는 사후 해석으로 발화를 취소하지 않는다.

## 2. 재는 것과 재지 않는 것

**주 지표(하나)**: `recall(N)` — 번들에 concept가 N개 있을 때, 사전에 동결한 질문 20개의 정답
concept 중 **게이트가 실제로 주입한 index 안에 링크가 살아남은 비율**.

**재지 않는 것 — 리포트에서 이 문장을 빼면 리포트는 무효다**:

> recall은 정답률이 아니다. 이 측정은 "게이트가 관련 줄을 실었나"까지만 답하고,
> "모델이 그 줄을 실제로 썼나"는 유료 호출 없이 확인 불가하다. 여기서 나온 어떤 숫자도
> 모델 성능·비용·정답률에 대한 주장으로 옮겨 쓸 수 없다.

## 3. 설계

| 항목 | 값 | 동결 위치 |
|---|---|---|
| 레벨 N | 24, 50, 100, 200 | `test/fixtures/bench/gate-recall.json` |
| 시드 | 1~20 (레벨당 20 표본) | 같은 파일 |
| 질문 | 20개 | 같은 파일 |
| distractor | 카테고리별 10개 × 6 = 60 | `test/fixtures/bench/gate-recall/distractors.json` |
| 형상 픽스처 | `live-shape-2026-07-26.json` | `test/fixtures/bench/gate-recall/` |
| 게이트 예산 | `inject_max_bytes` 9000 / `inject_max_lines` 120 | `lib/config.mjs` 기본값 |

**레벨 하한이 24인 이유**: 정답 concept 20개 + `ensureBootstrap`이 심는 시드 4개 = 24.
N=8이나 N=22는 **원리적으로 불가능**하다(정답을 다 심을 수 없다). 계획서 항목 15가 적은
더 작은 값들은 이 제약을 모르고 쓴 것이다.

**문항 구성 규칙**(같은 커밋에서 동결, 코드가 검사): 6개 카테고리 각 ≥2개, `answerConcept`
중복 0, `cwdIndependent` ≥6.

**정답 concept 조달**: 커밋된 실번들 14개(`docs/benchmarks/bundles/slim-L20` 8,
`bundles/rfcs-L20` 1, `bundles-chain-v4/chain-*` 5) + 직접 작성 6개(`authored: true`).
**라이브 번들 `~/.claude/okf`에서는 한 글자도 가져오지 않았다** — 사용자 지식 발행이 되기
때문이다. 형상 픽스처도 줄 바이트 길이와 더미 log만 담고 제목·설명 원문을 담지 않는다.

## 4. 계획서 사양에서 의도적으로 벗어난 3가지

사양을 그대로 따를 수 없었던 지점이다. **전부 측정 전에 결정했고, 하나도 임계 완화가 아니다.**

### (a) 홈 경로 길이 고정 → 인덱스 예산 역산

계획서는 tmp 홈 경로 길이를 고정해 `stats.headBytes`가 라이브의 686B와 같아지길 기대한다.
그러나 head는 `전역 지식 번들: ${okfHome}`으로 경로를 그대로 싣는다. 라이브 경로는 25자
(`~/.claude/okf`)인데 macOS tmpdir은 `/var/folders/...`라 **길이를 맞출 수 없다**
(실측 샌드박스 head 732B vs 라이브 686B).

대신 **인덱스에 주어지는 예산을 라이브와 일치시킨다**:
```
effectiveInjectMaxBytes = 6956 + 실측headBytes + 실측tailBytes   // 6956 = 9000 − 686 − 1358
effectiveInjectMaxLines =   92 + 실측headLines + 실측tailLines
```
그리고 매 샘플에서 `stats.budgetBytes + stats.headingBytes === 6956` 과
`stats.budgetLines + cats.length*2 === 92`를 검사해 어긋나면 `shape drift`로 **즉시 throw**한다.
(`stats.budgetBytes` 자체는 heading 선차감 **이후** 값이라 카테고리 개수 표기 자릿수에 따라
흔들린다 — 선차감을 되돌려 원 예산을 복원해 비교한다.)

이것은 G3-0b("하니스는 라이브와 같은 예산에서 잰다")를 **더 정확히** 만족한다. 샌드박스 경로
길이에 의존하지 않기 때문이다.

### (b) G3-0a의 5개 동결 값 재측정

계획서 G3-0a는 `taken 12/22`, 조립 **9,218B**, 절단 **218B**, 잔여 **58B**를 "오차 0"으로
요구한다. 그러나 그 값은 **예산 회계 수정이 착지하기 이전** 형상이다 —
`test/smoke.mjs`의 해당 주석 자신이 "수정 전에는 조립 9,218B / 절단 218B(전량 tail)였다"고
적고 있고, 현재 코드는 절단 0을 낸다. 옛 값을 그대로 단언하면 **R5가 오발화**한다
(`docs/0-2_benchmark.md` §2가 이미 예고한 상황이다).

그래서 새 픽스처 `live-shape-2026-07-26.json`에 **재측정값**을 못박는다. 기존
`test/fixtures/live-shape-2026-07-25.json`은 **손대지 않는다**(스모크가 쓰고 있고, 그 파일은
"수정 전에는 이랬다"는 사실의 기록으로서 여전히 유효하다).

| 값 | 2026-07-25(수정 전) | 2026-07-26(재측정, 이번 회차 기준) |
|---|---|---|
| taken / total | 12 / 22 | **12 / 22** |
| assembledBytes | 9218 | **8879** |
| truncatedBytes | 218 | **0** |
| leftoverBytes | 58 | **114** |
| cappedLines | (미기록) | **0** |

`taken`/`total`이 그대로인 것이 두 회계가 **같은 번들을 보고 있다**는 근거다. 바이트가 달라진
이유는 현재 `buildInjectedIndex`가 heading 최악값과 생략 마커를 조립 **전에** 선차감하고 다
담긴 카테고리에서만 환급하기 때문이다. `leftoverBytes`는 값이 커진 게 아니라 **회계 기준이
다르다**(58은 선차감 없는 잔여, 114는 선차감 후 잔여).

**R5는 이 재측정값 기준으로 판정한다.**

### (c) 생존 판정 정규식 — `- ` bullet → `* ` bullet

계획서는 생존 판정에 `/^- \[[^\]]*\]\((\/[^)\s]+)\)/`를 지정한다. 그러나 v0.2 index 포맷은
`* [제목](/dir/file.md) - 설명` 이라 **`- ` 가정이 한 건도 매치되지 않는다.** 실측: 계획서
정규식으로 센 생존 수는 **전 80 샘플 합계 0**이다.

하니스는 `* ` 기준 정규식을 쓰고, **계획서 정규식으로 센 값을 매 샘플에 병기해 JSON에
남긴다**(`planRegexSurvivorTotal`). 이 값이 0이 아니게 되면 포맷이 되돌아갔다는 뜻이므로
스모크 단언으로도 고정한다.

## 6. 반증 기준 R1 ~ R5 — 코드가 JSON에 boolean으로 찍는다

**임계는 계획서 라인 2322에서 문자 그대로 옮겼다. 이 문서 확정 이후 완화하지 않는다.**

| # | 발화 조건 | 발화 시 결론 |
|---|---|---|
| **R1** | `recall(50) ≥ 0.90` | 라우팅은 병목이 아니다 → **I2를 v0.3에서도 착수하지 않는다** |
| **R2** | `recall(24) < 0.60` | 실사용 규모에서 이미 실패 중 |
| **R3** | 레벨에 따른 단조 감소 위반 | **하니스 결함 — 전 결과 폐기** |
| **R4** | 어느 레벨에서든 시드 간 표준편차 > 0.25 | filler 명명에 지배됨 → **정책 결론 금지** |
| **R5** | 캘리브레이션 값 불일치(§4(b) 재측정값 기준) | **전 결과 무효** |

### I2 승인 조건

R1은 곧 **I2(게이트 라우팅 재설계)의 승인 조건**이다. 계획서가 I2를 v0.2에서 제외한 이유가
"라우팅이 병목인지 재는 장치가 없다"였으므로, 그 장치가 내는 값이 착수 여부를 정한다.

- `recall(50) ≥ 0.90` (**R1 발화**) → 게이트는 이미 관련 줄을 거의 다 싣고 있다.
  라우팅은 병목이 아니다 → **I2를 v0.3에서도 착수하지 않는다.**
- `recall(50) < 0.90` (R1 미발화) → 그 자체로 "I2를 하라"는 뜻은 **아니다.**
  R3·R4·R5 중 하나라도 발화하면 recall 절대값을 정책 근거로 쓸 수 없으므로,
  이 회차는 I2 착수 여부에 대해 **아무것도 결정하지 않는다.**

즉 이 측정이 단독으로 낼 수 있는 정책 결론은 **"I2를 하지 않는다" 한 방향뿐**이다.
반대 방향(착수)은 이 설계로 승인되지 않는다 — 그것은 별도 사전등록이 필요하다.

### R3에 대한 사전 규정 — 여기서 미리 못박는다

R3은 임계가 아니라 **부등식의 방향**이라 "노이즈"라는 사후 변명에 가장 취약하다. 그래서
이 문서가 확정하는 처리 규칙은 다음과 같다:

1. **발화하면 발화로 발행한다.** 델타가 표준편차보다 작아도 취소하지 않는다.
2. 발화 시 **recall의 절대값을 정책 근거로 쓰지 않는다.** 즉 R1·R2가 무엇으로 나오든
   그것으로 I2 착수 여부를 결정하지 않는다.
3. 발화 원인에 대한 가설(예: 레벨이 커지면 recall이 바닥에 붙어 평탄화한다)은
   **이번 회차에서 검증하지 않는다.** 다음 회차의 **별도 사전등록 대상**으로 넘긴다.
4. 하니스 건전성의 **독립 증거**(결정성 10/10, 예산 동형, 생존 집합이 심은 concept의
   부분집합, PATH 트랩 미발동, 훅 대비 바이트 동일)는 R3 발화와 **무관하게** 별도로 보고한다.
   R3이 "하니스 결함"을 규정하므로, 그 규정이 이 증거들과 충돌한다는 사실 자체가 발행 대상이다.

이 4개 조항은 R3의 발화 여부를 **바꾸지 않는다**. 발화 후에 무엇을 주장해도 되는지의 범위만
좁힌다.

## 7. 유료 0의 증명 방법 (G3-0d)

**`meta.paidCalls: 0` 같은 상수 선언은 하지 않는다 — 자기충족이다.**

- 훅 서브프로세스를 띄울 때 `PATH` 앞에 트랩 디렉토리를 붙이고, 그 안에 `claude`
  (win32는 `claude.cmd`) 스텁을 심는다. 스텁은 호출되면 `TRIPPED` 파일을 쓰고 exit 1 한다.
- 실행 종료 후 `meta.paidCallTrapTripped = fs.existsSync(trap)`를 JSON에 기록한다.
- 하니스 소스가 `/claude_bin|runClaude|fake-claude|OKF_RUN_LIVE_BENCH/`에 매치되지 않는 것을
  스모크가 단언한다.
- 훅을 띄우기 전 `okfPaths(home).lock`에 `{pid, startedEpochMs}`를 **선주입**한다. 빠지면
  detached 실배치가 떠서 개발 머신에서 **실제로 과금된다**.

## 8. 알려진 한계 (결과를 보기 전에 적는다)

1. **합성 distractor는 라우터 성능의 상한만 준다.** 실제 번들의 distractor는 정답과 주제가
   더 가깝다. 여기서 나온 recall은 낙관적이다.
2. **recall은 정답률이 아니다.** §2를 반복한다.
3. **라이브 형상은 n=1이다.** 하루치 번들 하나의 모양을 동결했다. 다른 날에는 다른 값이다.
4. **하니스는 동결된 `logMd`로 tail을 1358B/18줄에 고정한다.** 라이브 log.md가 그날 더 짧거나
   길면 index 예산이 달라진다. 이 회차의 숫자는 그 하나의 예산에 대한 것이다.
5. **직접 작성한 6개 concept가 곧 `cwdIndependent` 6개다.** 두 속성이 완전히 겹쳐 있어
   "저장소 독립성"의 효과와 "내가 쓴 문서"의 효과가 분리되지 않는다. P5가 반증되면 그 원인을
   이 설계로는 특정할 수 없다.
6. **파일명 사전순이 유일한 순서 결정자다.** 현행 게이트에는 cwd·최신성·질의어 참조가 0건이라,
   어떤 concept가 살아남는지는 사실상 카테고리 내 파일명 정렬이 정한다. recall의 분산은
   지식의 성질이 아니라 **명명의 성질**을 반영할 수 있다(R4가 이것을 잡으려는 것이다).
